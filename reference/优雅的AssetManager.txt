
重点：cpu资源对象和gpu对象往往不是一对一关系：比如texture复用，不像verticebuffer一样需要一一对应

完全会更优雅，也更符合现代游戏引擎设计理念。

核心思路是：

AssetManager 维护线程池（IO + CPU 可分离）
提交加载请求，类似提交 GPU command
AssetManager 自行调度，保证批量加载、线程利用率、依赖顺序
主线程只关心完成通知（callback / channel）

好处：

解耦：主线程不用管理线程，也不用关心具体加载实现。
批量优化：AssetManager 可以批量IO、缓存、合并小文件读取。
统一接口：像 GPU command 一样提交，让调用方接口简洁一致。
可扩展：以后加异步网络下载、解压、shader 编译，都可以放到同一个调度系统里。

💡 直觉比喻：

主线程像导演，只告诉演员“下一幕开始”，资源管理器像舞台经理，安排灯光、布景、演员动作（线程调度），导演不用管底层细节。

总结：这种设计在游戏引擎里是最优雅、最通用、最可维护的方案。


缓存的优雅方案
    核心思路
        1.线程池只负责加载
        每个线程拿到一个加载请求
        先查 CPU/Weak缓存
        如果缓存命中 → 返回 None（线程不更新缓存）
        如果缓存未命中 → 真正加载资源 → 返回 Some(Resource)
        2.主线程统一缓存
        收集线程返回的 Some(Resource)
        插入到缓存表（HashMap/Weak）
        更新 GPU 对象或其他依赖
    优势
        1.HashMap 不用全局锁
        线程只读取缓存
        写入缓存统一由主线程完成
        2.线程逻辑简单
        线程只负责 I/O + CPU解析
        不需要担心重复写 HashMap
        3.缓存管理可控
        所有缓存操作集中在主线程

Main Thread
    │
    ├── Render
    ├── ECS
    ├── Physics
    └── UI

Asset Thread
    │
    ├── Request Queue
    ├── Cache
    └── ThreadPool

缺点：如果直接在主线程调度AssetManager的线程调度的话会被阻塞（等待所以资源加载完成）导致程序无响应，所以解决方案是使用线程嵌套。
