# architecture/ —— 模块架构说明

> 面向**快速理解与定位**：每个模块一份"现状架构"文档，供开发者与 AI
> agent 在改动前建立正确的心智模型。只写现状与代码指向，不写历史。

## 文档分层（本目录与其他文档的边界）

| 位置 | 回答的问题 | 特征 |
|---|---|---|
| `CLAUDE.md` | 怎么干活（命令/约定/坑位） | 工作手册，所有人必读 |
| **`architecture/`（本目录）** | **模块现在长什么样、为什么这样设计** | **按模块组织，随代码演进** |
| `reference/` | 当时的决策过程与平台操作指南 | 决策记录 + how-to 指南 |
| `doc/log/` | 每天做了什么、为什么改 | 时间轴历史，不更新旧文 |

判断口诀：**改动前该读的放这里；当时为什么这么定的去 reference；某天改了什么去 doc/log。**

## 文档模板（固定八节，agent 可按节检索）

```markdown
# <模块>架构
> 一句话职责。
## 关键文件          # 文件 → 职责表（改动定位的入口）
## 架构与数据流      # 核心设计 + 数据怎么流
## 生命周期与运作模式 # 有状态者必配 mermaid 图（stateDiagram/flowchart，
                     #   Bird's eye view 风格——状态机、模式切换、背压循环）
## 公开 API 速览     # 对外面貌，标注对称性/命名约定
## 平台差异收敛点    # cfg 只允许出现在哪几处
## 设计纪律          # 不变量——改代码前必须知道的红线
## 测试锚点          # lib 测试 / probe 判读锚点
## 深入入口          # reference / doc/log 链接
```

> 图表约定：有状态周期（状态机/生命周期/运作模式）**必须用 mermaid 可视化**
> （GitHub 原生渲染），风格对齐根目录 `architecture.md` 的 Bird's eye view；
> 无状态纯函数式模块可省略此节。

## 维护约定

1. **架构级批次落地时，同步更新对应 `architecture/<模块>.md`**——
   与"写 changelog"同为批次收尾动作（此约定同时登记在 CLAUDE.md）。
2. 文档只陈述**现状**：设计背景去 `doc/log/` 找，本目录不追历史。
3. 代码是唯一事实源：文档与代码冲突时，先改文档或先修代码，不许共存分歧。
4. 新模块立项 = 新建对应文档（哪怕先只有关键文件表）。
